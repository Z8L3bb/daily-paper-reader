## 摘要
LiDAR（光探测与测距）传感器通过测量发射激光脉冲的飞行时间，将周围环境捕获为密集的三维点云，成为自动驾驶汽车、机器人技术和大规模测绘的基础。来自这些传感器的PCAP（数据包捕获）文件是大多数三维感知流水线的起点，然而各制造商在内部数据包结构、UDP（用户数据报协议）端口约定和编码方案上的差异足够大，以至于没有单一工具能全部读取。Ouster、Velodyne、Hesai和Livox各自需要自己的SDK（软件开发工具包）、自己的环境设置以及自己的转换工作流。同时支持这四种传感器意味着需要维护四个互不相连且没有共享基础设施的流水线。本文描述的流水线以原始PCAP作为输入，自动处理供应商识别，通过加权多信号方法对六个独立的文件特征进行评分，以确定源传感器。C++ SDK负责处理Ouster和Velodyne的数据，而Hesai和Livox则依赖基于Python的dpkt解析，因为缺乏开源的SDK。从那里，一条命令即可将输出写入五种行业标准格式中的任意一种。我们在真实室外采集的数据上进行了测试。Ouster的峰值处理速度为每秒208万个点，Velodyne为每秒147万个点，两者均通过原生C++数据包解码运行。Hesai和Livox分别为每秒11万和15万个点，其中Python层的解析引入了在持续负载下累积的开销。8到10倍的差距在多次运行中保持稳定。在配备8GB内存的消费级i3处理器上测试，无需任何供应商配置。

## Abstract
LiDAR (Light Detection and Ranging) sensors capture the surrounding environment as dense 3D point clouds by measuring the time-of-flight of emitted laser pulses, making them foundational across autonomous vehicles, robotics, and large-scale mapping. PCAP (Packet Capture) files from these sensors are the starting point of most 3D perception pipelines, yet internal packet structures, UDP (User Datagram Protocol) port conventions and encoding schemes differ enough across manufacturers that no single tool reads them all. Ouster, Velodyne, Hesai, and Livox each require their own SDK (Software Development Kit), their own environment setup, and their own conversion workflow. Supporting all four means maintaining four disconnected pipelines with no shared infrastructure. The pipeline described here takes a raw PCAP as input and handles vendor identification automatically, scoring six independent file characteristics through a weighted multi-signal approach to determine the source sensor. C++ SDKs handle Ouster and Velodyne, while Hesai and Livox rely on Python-based dpkt parsing where no open source SDK exists. From there, a single command writes output to any of five industry-standard formats. We tested on real outdoor captures. Ouster peaks at 2.08M points per second, Velodyne at 1.47M, both running through native C++ packet decoding. Hesai and Livox land at 110K and 150K respectively, where Python-layer parsing introduces overhead that compounds under sustained load. The 8-10x gap held consistently across runs. Tested on a consumer-grade i3 with 8GB RAM, no vendor configuration required

## 1. 论文的核心问题与整体含义

*   **核心问题**：不同制造商（Ouster, Velodyne, Hesai, Livox）的LiDAR传感器输出原始数据（PCAP）时，其内部数据包结构、UDP端口约定和编码方案存在显著差异，且各厂商提供互不兼容的私有SDK。这导致数据处理流程高度碎片化，研究人员和工程师不得不为每一个厂商维护独立的转换流水线，存在严重的工程负担和集成困难。
*   **整体含义**：本文旨在打破这种“供应商依赖”的壁垒，提出一个统一的、无需配置的工具链。其核心目标是从一份原始PCAP文件出发，自动完成传感器厂商的识别，并基于识别结果选择最佳解析后端，最终将数据批量转换为五种行业标准格式（PCD、LAS、LAZ、BIN、CSV）。该工作试图将厂商间的异构性完全下沉到管道内部，为用户提供一个端到端的“黑盒”转换体验。

## 2. 论文提出的方法论

*   **整体架构**：系统采用三层架构，包含“编排层”、“检测层”和“转换层”。用户通过统一的命令行界面交互，系统内部自动路由到对应模块。
*   **关键技术——加权多信号供应商检测**：
    *   系统并非依赖单一特征，而是从原始PCAP文件中提取六个独立信号，并根据其区分度分配权重，对候选供应商进行评分。得分最高且超过阈值（2.0）的供应商将被确定为数据来源。
    *   **六个检测信号及其权重**：
        1.  **UDP端口检测（权重3.5）**：解析前10个数据包的端口号，不同供应商使用明确且互不重叠的端口范围，故权重最高。
        2.  **魔数匹配（权重3.0）**：读取文件头部及数据包负载中的厂商特定签名（如 Velodyne 的 `0xFFEE`，Ouster 的 `0x0001`）。
        3.  **数据包结构验证（权重3.0）**：进一步在UDP负载级别匹配魔数，确认数据包级别的结构一致性。
        4.  **伴生文件检查（权重2.5）**：扫描同目录下的特定元数据文件（如 Ouster 必需的 `.json` 校准文件），作为强辅助证据。
        5.  **数据包大小统计（权重2.0）**：抽样50个数据包，检查其负载尺寸是否落在厂商特定的范围内。
        6.  **文件扩展名与文件名（权重0.5）**：提供初步的弱参考信息。
*   **转换策略与解析器分叉**：
    *   检测完成后，数据被路由至对应的“供应商特定包装器”。所有包装器继承自“基础包装器”，输出统一的 `N×4` `float32` NumPy 数组，再由基础包装器负责序列化为各种输出格式。

    *   **通用兼容路径（Python）**：针对缺乏开源 SDK 的 Hesai 和 Livox，系统采用纯 Python 的 `dpkt` 库实现底层数据包解析，并手动处理复杂的专有格式（如 Livox 的二进制 LVX/LVX2 格式点云）。
